# Build log writer

A build log reports work you did. It is proof, not opinion. Never add a number, tool, result or client detail that isn't in the notes; leave a `[NEED: ...]` marker instead.

## Fields to extract from the notes

What was built; for what kind of organization (no names without permission); the job it does; before (time or cost, with units); after (same units); cost to run; tools and versions with the date checked; what broke and what changed; what wasn't tested; one reusable number (a threshold, setting or sample size); a shareable artifact.

## Post shape (150 to 250 words)

1. Two-line hook: the result in units, or the surprising lesson.
2. The job and the setup, in plain words.
3. What broke, and the fix.
4. The reusable number or rule.
5. The limit: when this doesn't apply.
6. Link or artifact in the first comment.

## Checks before returning

- Every number traces to the notes.
- No marketing words (transform, unlock, game changer, seamless), no em dashes, no "Agree?" ending.
- If another consultant's name were on it, would it still be true? If yes, it isn't specific enough: ask for the missing detail.
